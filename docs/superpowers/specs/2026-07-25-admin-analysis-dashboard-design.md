# 管理分析端信息架构与页面设计

日期：2026-07-25
状态：已确认设计，待实施计划
适用范围：管理分析端 D1、D2、D3

## 1. 背景与问题

第一版管理端已具备数据总览、需求分析、双方差异和两类答卷查看能力，但页面主要采用数字卡、字段列表和三栏文本，存在三个问题：

1. 数据总览将多张图表平铺在同一屏，管理员第一眼难以识别重点；
2. 需求分析更像需求详情，Agent 得出了什么结论、结论依据是什么不够突出；
3. 双方差异只并列显示员工与负责人引用，没有结构化说明哪些信息一致、互补、缺失或明确不同。

本次设计不扩大产品范围，不增加需求池、立项、审批、管理员评分或员工排名。目标是用更清晰的信息架构和可视表达，帮助管理员发现需求线索、理解单条需求并追溯证据。

## 2. 设计目标

管理员应能在打开页面后的短时间内回答：

- 当前批次最值得继续了解的需求线索是什么；
- 某条具体需求是什么，Agent 分析了哪些内容；
- 员工与负责人分别提供了哪些证据；
- 哪些信息一致、互补、缺失或明确不同；
- 结论来自哪些答卷，当前还缺什么信息。

成功标准：

- D1 首屏只展示关键数字、三条重点发现和一张证据结构摘要；
- D2 首屏明确显示 Agent 初步分析结论、事实信号、分析路径和待补信息；
- D3 首屏能逐维识别员工与负责人证据覆盖及关系类型；
- 所有 Agent 结论均能进入来源证据或原始答卷；
- 任意数量、比例、覆盖关系均有明确分母和统计口径；
- 页面不生成优先级总分、员工总分、岗位排名或建设结论。

## 3. 命名与页面职责

管理端左侧导航保持三项分析入口：

| 导航名称 | 页面职责 | 核心问题 |
| --- | --- | --- |
| 数据总览 | 发现当前批次重点 | 当前最值得管理员关注什么？ |
| 需求分析 | 理解一条具体需求 | 这是什么需求，为什么值得继续了解，还缺什么信息？ |
| 证据对比 | 比较员工与负责人证据 | 双方分别提供了什么，哪些一致、互补或缺失？ |

“双方差异”统一改为“证据对比”。原因：

- “双方”没有明确说明员工与负责人；
- “差异”容易把未提及误解为意见冲突；
- 页面实际比较的是来源证据覆盖和内容关系。

D3 页面完整标题可使用“员工与负责人需求证据对比”，左侧导航使用短名称“证据对比”。

## 4. 页面关系

```text
数据总览 D1
├─ 重点概览
├─ 需求分布
│  ├─ 按需求看
│  └─ 按岗位看
└─ AI 使用现状
   ├─ AI 使用情况
   └─ 员工画像

重点发现或具体需求
→ 需求分析 D2
   ├─ 分析结论
   ├─ 来源证据
   └─ 原始答卷

跨需求证据状态
→ 证据对比 D3
   └─ 选择具体需求后逐维比较员工与负责人证据
```

D2 中不再使用“证据对比”作为页内标签，避免与 D3 重复。D2 的“来源证据”负责展示所选需求的引用依据，D3 负责结构化比较两类来源。

## 5. D1 数据总览

### 5.1 页面主题

D1 负责发现问题，不承担完整数据探索。一级视图只有：

```text
重点概览｜需求分布｜AI 使用现状
```

### 5.2 重点概览

核心问题：当前批次最值得继续了解什么？

页面只保留两个主要区域：

1. 左侧重点发现：约占内容区 65%；
2. 右侧需求证据结构摘要：约占内容区 35%。

顶部关键数字最多三项：

- 有效答卷；
- 具体需求；
- 值得继续了解的需求线索。

重点发现最多三条，每条必须包含：

- 结论；
- 适用范围；
- 有效来源数量；
- 当前证据状态；
- 进入需求分析的入口。

证据结构摘要只展示：

- 双方均有证据；
- 员工侧证据更明显；
- 负责人侧证据更明显；
- 当前证据较少。

此处不显示优先级、建设价值或员工排名。

### 5.3 需求分布

核心问题：收集到了哪些具体需求，分别出现在哪些岗位？

同一页面提供两个观察角度：

```text
按需求看｜按岗位看
```

“按需求看”以具体需求场景为主体，至少展示：

- 具体需求名称；
- 所属能力或需求方向标签；
- 员工与负责人来源构成；
- 涉及岗位；
- 当前证据状态；
- 进入 D2 的入口。

“按岗位看”使用带数值的岗位矩阵：

- 行为岗位；
- 列为具体需求或经过筛选的需求方向；
- 单元格显示 `提及人数/该岗位有效样本数`；
- `0/n` 表示存在样本但未提及；
- `—` 表示没有有效样本；
- 颜色表示岗位内提及比例，不能表示优先级；
- 小样本使用独立提示，不形成岗位共性结论。

### 5.4 AI 使用现状

核心问题：员工现在如何使用 AI，整体表现出怎样的使用特征？

页面包含两个相关模块：

1. AI 使用情况：使用频率、常见工具、使用场景、未使用原因和主要障碍；
2. 员工画像：六维行为画像、维度值、有效样本数和维度解释。

“员工画像”名称保留，但不单独占用一级分页。页面不计算员工总分或排名。

## 6. D2 需求分析

### 6.1 页面主题

核心问题：这是什么需求，为什么值得继续了解，现在还不能判断什么？

D2 仍采用左侧需求清单、右侧所选需求分析的工作台结构。右侧内容采用“结论先行，依据后置”。

### 6.2 左侧需求清单

每项至少展示：

- 具体需求名称；
- 一句话任务摘要；
- 来源数量；
- 涉及岗位；
- 当前证据状态。

支持按批次、部门、岗位、证据状态筛选和按名称搜索。切换需求不整页刷新，URL 同步 `selected` 参数。

### 6.3 Agent 初步分析结论

右侧首要模块必须用一段话回答：

- 需求是什么；
- 哪些事实支持继续了解；
- 可能的 AI 支持方向；
- 仍需验证的条件。

结论必须标注为“Agent 初步分析”，不得写成立项建议、优先级或已经确认的技术方案。

### 6.4 需求信号看板

信号看板只展示事实，不生成综合评分：

- 发生规律；
- 步骤稳定程度；
- 覆盖人群或岗位；
- 员工与负责人来源数量；
- 信息完整度。

信息完整度沿用 `complete / partial / insufficient` 的离散状态。只有建立确定性字段检查规则时才能显示 `x/n`，不得由模型生成未经定义的百分比。

### 6.5 分析路径

页面以可视路径表达 Agent 的分析过程：

```text
实际任务 → 当前做法 → 核心问题 → 可能支持方向 → 建设前提
```

前四项来自答卷事实与可追溯归纳；“建设前提”展示当前缺失信息和后续需了解的问题，不代表已经进入建设阶段。

### 6.6 详细内容

分析路径下方保留三个模块：

- 事实依据；
- 原始期望与可能支持；
- 后续需要了解。

页内标签统一为：

```text
分析结论｜来源证据｜原始答卷
```

## 7. D3 证据对比

### 7.1 页面主题

核心问题：员工和负责人分别提供了哪些证据，哪些一致、互补或缺失？

D3 先展示当前批次证据状态分布，再选择一项具体需求进行逐维比较。

### 7.2 批次级摘要

页面顶部展示四类数量：

- 双方均有证据；
- 员工侧更明显；
- 负责人侧更明显；
- 当前证据较少。

“明确表达不同”只有真实存在时才展示为单独状态，不使用红色将未提及表示为冲突。

### 7.3 证据覆盖镜像图

选中需求后，通过左右镜像图逐维展示员工与负责人证据覆盖：

- 左侧为员工来源覆盖；
- 中间为比较维度和关系标签；
- 右侧为负责人来源覆盖；
- 两侧均显示 `覆盖该维度的来源数/该侧有效来源总数`。

第一版固定比较维度：

1. 实际工作场景；
2. 主要问题；
3. 期望支持方向；
4. 人工确认边界；
5. 系统与数据条件。

允许的关系标签：

- 双方均提及；
- 信息互补；
- 方向基本一致；
- 员工侧补充；
- 负责人侧补充；
- 员工侧未提及；
- 负责人侧未提及；
- 双方均未说明；
- 明确表达不同；
- 样本不足。

镜像条表示来源对该类信息的覆盖情况，不表示观点强弱、认可程度或评分。

### 7.4 逐维内容矩阵

镜像图下方保留四列内容矩阵：

| 比较维度 | 员工侧具体内容 | 对比结果 | 负责人侧具体内容 |
| --- | --- | --- | --- |

矩阵负责解释图表。原始引用默认收起，管理员可以展开来源证据或进入 D2、员工答卷、负责人答卷。

## 8. 数据契约与来源追溯

### 8.1 可直接复用的数据

当前 `AggregateScenario` 已包含：

- 标题、摘要、当前做法和主要问题；
- 发生规律、稳定程度和覆盖人群；
- 原始期望、可能支持方向和后续问题；
- 部门、岗位、来源数和覆盖人数；
- 员工证据、负责人证据和证据状态；
- 信息完整度和来源答卷。

D2 的主体内容可以基于这些字段实现。

### 8.2 需要补充的数据

D3 镜像图和逐维矩阵不能仅凭现有引用数组可靠生成。聚合结果需要增加结构化字段：

```ts
interface EvidenceDimensionComparison {
  dimension: 'task_context' | 'main_problem' | 'expected_support' | 'human_boundary' | 'system_data_conditions';
  employeeSourceCount: number;
  employeeSourceTotal: number;
  positionSourceCount: number;
  positionSourceTotal: number;
  relation: 'both_mentioned' | 'complementary' | 'direction_aligned' |
    'employee_supplement' | 'position_supplement' | 'employee_missing' |
    'position_missing' | 'both_missing' | 'explicit_conflict' | 'insufficient_sample';
  employeeSummary: string;
  positionSummary: string;
  employeeSourceIds: string[];
  positionSourceIds: string[];
}
```

约束：

- 来源数量必须由有效来源 ID 确定性计算，不能由模型猜测；
- 模型只负责归纳两侧内容和关系类型；
- 每个摘要和关系必须保留来源 ID；
- 问卷更新后，相关维度比较与聚合结果需要失效并重新计算；
- 样本不足时保留来源入口，不输出岗位共性或趋势结论。

D1 的 AI 使用情况、常见场景和主要障碍需要从员工答卷字段进行固定统计，并扩展管理端 DTO；不由模型生成数量。

## 9. 视觉与交互规范

整体采用“深海蓝 + 极光青蓝”的专业后台风格：

- 深蓝为主背景；
- 青色表示当前选中、双方均有证据或主要交互；
- 蓝色表示员工侧信息；
- 紫色表示负责人侧补充或负责人证据更明显；
- 橙色只表示信息缺失、小样本或需要继续了解；
- 不使用红色表达未提及；
- 不使用持续流光、粒子背景或装饰性大屏动画。

图表必须遵循：

- 颜色有稳定语义；
- 去掉颜色后仍能通过位置、长度、数值和文字读懂；
- 数量显示分母；
- 图表与下方文字解释同一件事，不增加独立口径；
- 一屏最多两个主要视觉区域；
- 详细引用默认后置或折叠。

## 10. 页面状态

每个页面必须覆盖：

- 默认状态；
- 加载状态；
- 无数据状态；
- 聚合分析中；
- 聚合分析失败；
- 分析已过期并重新计算；
- 小样本状态；
- 部分来源缺失；
- 来源答卷已更新或不可用。

错误或过期状态不得展示旧版 Agent 结论为当前结论。原始答卷和固定统计仍保持可访问。

## 11. 响应式策略

桌面端优先，内容宽度充足时采用左侧清单和右侧工作区。

小屏策略：

- D1 一级视图横向滚动或使用紧凑切换；
- D2 先展示需求清单，选择后进入同路由详情；
- D3 镜像图保持维度顺序，内容矩阵改为逐维卡片；
- 不通过缩小文字强行保留桌面三栏结构。

## 12. 验收标准

### D1

- 重点概览只出现三项关键数字、三条重点发现和一张证据结构摘要；
- 需求分布支持按需求和按岗位两种视角；
- AI 使用现状同时展示使用情况和员工画像，但不生成员工总分。

### D2

- 选择需求后，首屏可以看到 Agent 初步结论和事实信号；
- 分析路径完整展示五个节点；
- 事实、Agent 归纳和待补信息有明确区分；
- 可以进入来源证据和原始答卷；
- 页面不提供评分、立项、审批或管理员编辑动作。

### D3

- 可以按需求查看员工与负责人五个维度的证据覆盖；
- 每个覆盖条显示来源数和分母；
- 每个维度显示明确的关系标签；
- `0/n`、未提及、明确不同和样本不足不会被混为同一状态；
- 逐维矩阵内容可追溯到具体来源答卷；
- 可以进入 D2 查看完整分析。

## 13. 非目标范围

- 需求池、建设状态、审批、驳回和责任人分配；
- 管理员逐项打分；
- 员工总分、岗位总分和排名；
- 根据提及次数自动生成优先级；
- 将未提及解释为意见冲突；
- 自动确认技术可行性、数据安全边界或建设结论。
